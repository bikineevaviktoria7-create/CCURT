# Правила перехода на ООП (обязательны для каждого шага этапа ООП)

Этот файл дополняет `dop/REFACTOR_RULES.md`. Всё, что там сказано, действует и здесь, **кроме** пунктов, прямо изменённых ниже.
На этапе ООП code-architect работает в **режиме ООП**, но только в границах, указанных в задаче шага.

## 1. Что меняется по сравнению с REFACTOR_RULES.md
- **Разрешено** переводить на классы объекты с состоянием и жизненным циклом, указанные в задаче шага.
- **Разрешено** в `dop/tests` менять способ создания объектов (`createX(...)` → `new X(...)`), импорты и ключи подмены модулей. Логику проверок (assert, ожидаемые значения) менять **нельзя**, тесты не удалять и не пропускать.
- **Разрешено** переименовывать фабрики/файлы из списка кандидатов волны 3 `dop/STYLE.md`, если это нужно для класса (например, `createMockVision` → класс `DemoVisionAdapter`).
- Всё остальное из раздела 2 REFACTOR_RULES.md в силе: числа, тексты, ключи хранилища, формат samples.json, Supabase, маршруты, CSS, пакеты — не меняются.

## 2. Как писать классы (иначе упадут тесты или сборка)
- У каждого класса — `interface` с публичными методами; класс `implements` его. Код снаружи зависит от интерфейса.
- Зависимости (хранилище, Supabase-клиент, часы, другие сервисы) — через конструктор, чтобы в тестах подставлять заглушки.
- Поля объявлять явно и присваивать в конструкторе. **Запрещено**: параметры конструктора с `private/public/readonly`, `enum`, `namespace`, декораторы — их не понимает `node --experimental-strip-types`, на котором идут тесты. Модификатор `private` у обычного поля — можно.
- Импорты в чистых модулях — с расширением `.ts`, типы — через `import type` (как сейчас).
- Методы, которые передаются как колбэки, объявлять стрелочными полями или привязывать, чтобы не потерять `this`.
- **Имена экспортов-экземпляров не меняются**: если был `export const progressService = {...}`, после шага остаётся `export const progressService = new ProgressService(...)` (или фабрика с тем же именем). Так страницы и хуки не нужно переписывать.
- Чистые функции без состояния (нормализация, признаки, расстояния, DTW, calculateLessonResult и т. п.) **остаются функциями**. Класс ради класса не создаётся.
- React-компоненты и хуки остаются функциональными. `ErrorBoundary` уже класс — не трогать.
- Одна ответственность на класс. Наследование — только там, где есть настоящее «является» (два адаптера реализуют один интерфейс); иначе композиция.

## 3. Проверка шага (в дополнение к разделу 4 REFACTOR_RULES.md)
- Число тестов не меньше 59 (или текущего значения в `.qa/baseline.md`).
- Если шаг затрагивает `src/vision` или адаптеры — cv-engineer прогоняет старую (HEAD) и новую версию на эталонах из `public/data/samples.json` и синтетических кадрах и подтверждает **0 расхождений** в результатах распознавания.
- Если шаг затрагивает сервисы — backend-engineer подтверждает по diff, что запросы к Supabase, ключи хранилища и порядок операций не изменились.
- Проверка «поведение не изменилось» (п. 6 раздела 4): новые классы и перенесённый код дадут много строк — для каждого числа/русской строки/ключа хранилища объясни, что оно просто переехало без изменений.

## 4. Git и остановка
- Коммиты делает только человек. Агентам разрешены `git status`, `git diff`, `git log` и `git restore <файл>` для отката своих изменений при провале.
- Если шаг оказался больше ожидаемого или заканчивается контекст — остановись в состоянии, где всё собирается и тесты проходят, и напиши «НЕ ЗАВЕРШЕНО» со списком оставшегося.
